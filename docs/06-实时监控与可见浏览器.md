# 实时监控 / 人工可见操作（v0.4.1）

**出现新 Job，但 Jenkins 显示 `No builds` 不等于 Build 成功或脚本冻结。**

检查顺序：
1. `./app-build status` 获得 TASK_ID、阶段及运行状态。
2. `./app-build watch TASK_ID` 查看 Worker 是否进入 `PLUGIN_JENKINS`，是否发现 Job，是否识别出 `Build with Parameters`。
3. 查找 `[CLICK]`（点击操作）、`[JENKINS]`（Job 和编号）、`[WAIT]`（等待原因）消息。
4. 没有 `[CLICK]` 不能推断构建已触发；不要在页面上人工多次点击。
5. 若截图显示 `No builds` 但识别到了参数入口，新 Job 可以直接进入正式参数化构建，不强制初始化构建。
6. 如果变成 `NEEDS_ATTENTION`，检查任务目录 `runs/TASK_ID/screenshots/`，核实页面入口；再决定是否恢复。

| 期望场景 | 命令 | 是否会改动当前正在运行的 Worker |
|---|---|---|
| 新任务实时进度 | `./app-build run ... --watch` | 新建任务 |
| 新任务所有操作可见 | `./app-build run ... --watch --verbose --visible` | 新建任务 |
| 查看现有任务 | `./app-build watch TASK_ID` | 否 |
| 旧日志兼容模式 | `./app-build logs TASK_ID --follow` | 否 |
| 退出后调试恢复 | `./app-build resume TASK_ID --watch --visible --verbose` | 只允许原 Worker 已停止 |

**安全约束**：不会输出 Token 值、不会调用 Jenkins API、不会因观看日志而额外触发 Build。GUI 模式使用本机 Chrome，必须先按 README 登录对应 Jenkins。保留本地认证和日志，不能共享给外部人员。

## 完整操作流水（v0.4.1）

```bash
# 推荐：一条命令启用进度心跳 + 可见 Chrome + 全操作流水
./app-build run --plugin-branch develop --plugin-version 1.3 \
  --gmx-branch develop --country UK --project-name PayByBank --live

# 如果不希望弹出 Chrome：仅终端详细日志 + 心跳
./app-build run --plugin-branch develop --plugin-version 1.3 \
  --gmx-branch develop --country UK --project-name PayByBank --watch --verbose

# 已停止任务继续，打开可见浏览器并输出流水
./app-build resume TASK_ID --live

# 已在运行的旧任务：仅查看其当时写入的日志，不能追溯尚未记录的旧操作
./app-build watch TASK_ID
```

- `[TRACE]` 显示完整 Git 命令（从不展开 GitHub Token）；`[GIT]` 显示返回码与耗时；`[GIT-OUT]` 显示已清理的 Git 输出。
- `[PW]` 显示 Playwright 业务操作：启动浏览器、打开 URL、读取表单、定位控件、`click`、`fill`、`check`、`select_option`、扫描 Build Number、检查结果和 Artifacts。
- `[CLICK]`、`[JENKINS]`、`[WAIT]` 保留更易读的业务事件；`[SHELL]` 显示子进程命令与退出码；`[BOOTSTRAP]` 在 verbose 模式下实时跟随 `./bootstrap.sh` 输出。
- 全部日志在当前任务 `run.log`；bootstrap 的逐行清理后的输出还单独记录在 `bootstrap.log`。日志经过**尽力而为**的敏感值隐藏，不能保证自动识别所有业务敏感信息。不要上传/分享真实公司 CI 日志。
- Playwright 日志对应**项目调用的操作**，而不是 Chromium 的每个内部渲染动作、网络请求或浏览器内部重试。不会自动记录 HAR、Cookie、Authorization Header 或 DOM 快照；避免泄露认证数据。
- 对已经启动的后台任务，修改脚本或运行 `watch` 不会让原 Worker 动态变为 verbose。只能安全等待其退出后使用 `resume TASK_ID --live`；不要在任务运行中重复触发 Jenkins 构建。


## v0.4.2：Plugin Trigger → Callback 状态切换

公司 Jenkins 的 `release-build` 可能先完成一个轻量触发器 Build（如 `#1 Manual Trigger`），随即创建实际执行 Build（如 `#2 Manual Callback ← Source #1`）。`#1` 的 Jenkins 控制台不一定包含 `Finished: SUCCESS` 标记，而且新版页面顶部状态 SVG 不属于旧版 `#build-status-icon` 选择器。v0.4.2 同时识别新旧状态图标，并在源构建状态未判定时检查 **明确的 Source 编号关联**：

```text
[JENKINS] plugin 正在监控 Build #1
[CALLBACK] plugin Build #1 已创建关联 Callback #2；切换监控 #2
[CALLBACK] Plugin Trigger #1 → Callback #2；下一步监控 Callback
[JENKINS] plugin 正在监控 Build #2
[JENKINS] plugin Build #2 页面图标确认终态: SUCCESS
[ARTIFACT] ... Build #2
```

可从未完成的旧任务用 `resume TASK_ID --live` 接续，只要原 Worker 已退出；已持久化的 `plugin_formal_number` 与 `plugin_callback_number` 防止重复点击 Build。若失败、出现多个同源 Callback 或无法确认 Source 关系，仍会停止人工检查，而不是猜测。
